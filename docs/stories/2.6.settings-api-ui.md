# Story 2.6: Settings API and client UI

## Status
Draft

## Story
**As a** user,
**I want** to choose my preset, default mode, per-app modes, insert behaviour, language and hotkey,
**so that** Sayvox behaves the way I work.

## Acceptance Criteria
1. `GET/PUT /v1/settings` with Zod validation; cached in Redis (5 min TTL, invalidated on write).
2. Client caches settings at start and on change; Settings UI (General, Modes, Preset) per `docs/front-end-spec.md`.
3. Plan-disallowed presets are rejected with `403` and shown locked in the UI.

## Tasks / Subtasks
- [ ] `apps/api/src/modules/settings/`: GET (cache-aside `settings:{userId}`), PUT (validate, write, `DEL` cache) (AC 1)
- [ ] Validate `appModeOverrides` ≤ 100 keys, app ids pattern, modes enum (AC 1)
- [ ] Preset check against `plans.allowed_presets` → `403 FORBIDDEN` (AC 3)
- [ ] Client settings store hydrated on start; optimistic update with rollback on error (AC 2)
- [ ] Settings window shell with sidebar (General, Modes, Preset, Dictionary, Usage & Plan, Privacy & Account) (AC 2)
- [ ] General: HotkeyRecorder, Insert mode (Auto/Review), Language (Auto, English, English-India, Hinglish), Launch at login, Mic device (AC 2)
- [ ] Modes: default mode select; overrides table with running-app picker; built-in suggestions (AC 2)
- [ ] Preset: three cards with speed/cost hints, locked state (AC 2, 3)
- [ ] Contract test `apps/api/test/contract/settings.test.ts` (AC 1, 3)

## Dev Notes
- Screen specs: `docs/front-end-spec.md` §4; data: `data-model.md` `settings`.
- Keyterms cache shares the settings cache entry so `/session/start` needs one Redis read.
- Accessibility: WCAG AA, full keyboard navigation (front-end spec §6).

### Testing
